# Fallible allocation SDK source profile

Every enclave build compiles against this source profile. It adds an explicit
fallible allocator ABI and sealed-buffer API to the pinned SDK and makes
Builder name, thread/packet/closure and native task-node allocations return an
error. It does not enable a global allocator, replace the C allocator, or
qualify total TLS, thread, futex or heap accounting.

The manifest binds original and patched files plus patch bytes. Apply it only to
a new task-owned copy of the already reviewed SDK source; verify every before
file, patch hash and after file. Keep the original SDK unchanged. Cargo and the
std build must use the same copy.

CMake includes all manifest paths, including the new allocator module, plus
the manifest and patch hashes in the sysroot input identity. Its input ID owns
fresh std outputs; a reused historical sysroot cannot establish this profile.
Changes to CMake provenance require a fresh input identity; old binary
identities are never relabelled.

The explicit allocator admits the complete backend layout, including its private
header and alignment padding, before allocating. Reallocation admits the full
new block while the old block remains live. Deallocation frees backend storage
before releasing the original owner and loan. Admission callbacks must be
nonallocating, non-unwinding and valid until the final deallocation. These are
resource rules, not application or signing authority.

The native model and allocator API checks are private development evidence.
They do not substitute for actual SDK/std compilation, connected constructors,
signed SIM or the original trusted runtime owning checks. The manifest's
remaining items must close before enforcement or final allocator qualification.

Reproduce source acquisition with the tracked helper. The reviewed source is
the pinned revision with the SDK 2.30 crypto, libunwind compatibility,
reproducible-sysroot and Autotools patches applied, extracted with its Git
file modes:

```sh
python3 scripts/prepare-fallible-allocation-sdk.py \
  --source /absolute/reviewed-sdk-source \
  --identity /absolute/pinned-sdk-git-checkout \
  --destination /absolute/new-build/sdk-source
```

Configure the build with
`HONEST_PINNED_TEACLAVE_FALLIBLE_SOURCE=/absolute/new-build/sdk-source`.
The selected source must be inside this build directory. The original identity
checkout still supplies the pinned tree enumeration; the selected mirror and
additional manifest files supply actual hashes. Cargo's acquired dependency
configuration must select this same mirror, and the compiler namespace must
mount it read-only. A mismatched source or old sysroot must fail; there is no
unpatched SDK path.

Before configuring a read-only compiler mirror, run the adjacent
`prepare-inputs.sh MAIN_SOURCE ORIGINAL_SDK NEW_AUTOTOOLS_OUTPUT` with
`approved-functions.sh` alongside it. These are the exact reviewed network-off
Autotools generation and refusal owners, tied to their source/tool hashes. Run
it at the paths the compiler presents: the receipt binds the absolute helper
paths CMake later reads. `approved-functions.sh` is the sole owner of those
functions; the manifest pins it and this script. The receipt describes
input generation; it is not a claim that a HW or SIM compiler has run.

Copy the receipt's `source` tree over the owned SDK mirror, set
`HONEST_TEACLAVE_PREGENERATED_AUTOTOOLS=1`, and pass
`HONEST_TEACLAVE_FALLIBLE_AUTOTOOLS_RECEIPT=.../input-receipt.json`. CMake checks
all generated bytes and incorporates their receipt and actual paths into the
std input identity. Generated source, input provenance and std outputs stay
separate. Neither the original checkout nor any historical sysroot is changed.
The parent repository's `scripts/ci/lib/prepare-fallible-sdk-inputs.sh` performs
this whole recipe, including a re-execution of the refusal sentinels, for every
enclave build.
